# 3 つの領域

Git を触りはじめて最初に戸惑うのは、`add` と `commit` を**2 回に分けて打つ**ことだと思います。
保存したいだけなのに、なぜ 2 段階なのか。

答えは、Git が値を持つ場所が 3 つあるからです。

| 領域 | 何が入っているか | ここへ運ぶコマンド |
| --- | --- | --- |
| 作業ディレクトリ | 編集しただけで、まだ Git に渡していない変更 | `touch` / `edit`（エディタでの編集） |
| ステージ (index) | 次のコミットに含めると決めた変更 | `git add` |
| リポジトリ | コミットとして確定した履歴 | `git commit` |

`add` は「作業ディレクトリ → ステージ」、`commit` は「ステージ → リポジトリ」。
それだけです。2 段階なのは、**運ぶ先が 2 回あるから**でした。

## ステージは「下書き」です

なぜ間に 1 枚挟むのか。**コミットに何を含めるかを選べるようにするため**です。

```bash
touch a.txt
touch b.txt
git add a.txt        # a.txt だけをステージへ
git commit -m "a を追加"   # b.txt は入らない
```

`b.txt` は作業ディレクトリに残ったままです。
「直したいことが 2 つ混ざってしまったので、コミットは分けたい」というときに、この 1 枚が効きます。

## サンドボックスでの見え方

コマンドを打つと、**書き換わった領域だけが一瞬光ります**。

| コマンド | 光る領域 |
| --- | --- |
| `touch a.txt` | 作業ディレクトリ |
| `git add a.txt` | 作業ディレクトリ・ステージ |
| `git commit -m ...` | ステージ・リポジトリ |

`add` で 2 つ光るのは、片方から減って片方に増えるからです。運んでいるのが目で見えます。

## untracked と modified

作業ディレクトリのファイルには 2 種類あります。

- **untracked** … 一度もコミットされていない。Git はこのファイルをまだ知らない
- **modified** … コミット済みだが、そのあと変更された

区別があるのは、Git が「変更」を**前のコミットとの差**として捉えているからです。
前が無いファイルは、差ではなく丸ごと新規なので、扱いが別になります。

このサイトでは `touch` が untracked を、`edit` が modified を作ります。
どちらも Git のコマンドではなく、エディタでの操作にあたるものです。

## どこを比べているのかを、diff で見る

3 つの領域があるということは、**比べ方も 3 通りある**ということです。
`git diff` の引数の違いは、そのまま「どことどこを比べるか」の違いです。

```bash
git diff              # 作業ディレクトリ ↔ ステージ
git diff --staged     # ステージ ↔ HEAD
git diff <commit>     # そのコミット ↔ 作業ディレクトリ
```

いちばん引っかかるのが 1 つ目です。

```bash
edit bouquet.txt 春の花
git diff              # 差分が出る
git add bouquet.txt
git diff              # 何も出ない！
```

`add` した瞬間、作業ディレクトリとステージが同じ中身になります。
だから 1 つ目の `diff` は空になります。**変更が消えたわけではありません。**
ステージへ移ったので、比べる相手が変わっただけです。`--staged` を付ければ出てきます。

「変更したのに diff が空」で戸惑うのは、ほぼこれです。
コマンドを覚えるより、3 つの領域のどこを見ているのかに戻るほうが早く解けます。

## このサイトでの簡略化

本物の Git のステージ（index）は、ファイルの**中身**のスナップショットを持っています。
このサイトも同じで、行の配列として中身を持ちます。

ただし扱うのは短い行だけです。文字単位の差分（1 行の中のどこが変わったか）や、
バイナリファイルまでは踏み込んでいません。
