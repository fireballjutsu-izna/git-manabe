# bisect ― いつ壊れたかを半分ずつ探す

> 昨日は動いていたのに、今日は動かない。そのあいだにコミットは 60 個ある。

このとき、新しいほうから 1 つずつ戻して試す人が多いです。
運が悪ければ 60 回試すことになります。

`git bisect` は、**半分に割って**探します。60 個なら 6 回です。

## 回数の差

| コミットの数 | 1 つずつ戻す（最悪） | 半分に割る |
| --- | --- | --- |
| 8 | 8 回 | 3 回 |
| 60 | 60 回 | 6 回 |
| 1000 | 1000 回 | 10 回 |

倍に増えても 1 回しか増えません。ここがこのコマンドの値打ちです。

## 挟み方 ― bad は新しい側、good は古い側

探すには、**壊れているところ**と**まだ動いていたところ**の 2 点が要ります。

```bash
git bisect start
git bisect bad             # いまここは壊れている（省略すると、いまいる場所）
git bisect good a1b2c3d    # ここは動いていた
```

この 2 点で挟んだ内側が、探す範囲です。

```
* 8つ目      ← bad（壊れている）
* 7つ目
* 6つ目
* 5つ目          この 6 個のどれかで壊れた
* 4つ目
* 3つ目
* 2つ目
* 1つ目      ← good（動いていた）
```

`git bisect good` を打つと、Git はまん中のコミットへ**勝手に移動します**。
HEAD が動くので、そのつど中身を確かめられます。

```bash
cat shop.txt          # このサイトでは cat で中身を読めます
```

動いていれば `git bisect good`、壊れていれば `git bisect bad`。
答えるたびに範囲が半分になり、グラフの帯が狭まっていきます。

## 判定できないとき ― skip

「この版はそもそもビルドが通らない」ということが起こります。
そのときは good とも bad とも答えず、飛ばします。

```bash
git bisect skip
```

飛ばしたぶんは候補から外れ、別のコミットが選ばれます。
飛ばしすぎると「残ったのは飛ばしたものだけ」になって、そこから先は絞れません。

## 終わったら reset を忘れない

探しているあいだ、HEAD は枝から外れています（detached HEAD）。
見つけただけでは、そこに置き去りのままです。

```bash
git bisect reset       # 始める前の枝へ戻る
```

これを忘れると、次に `git commit` したときに
「コミットしたのに、どの枝も伸びていない」が起こります。
[detached HEAD](/docs/detached/) と同じ話です。

## 見つかるのは「壊れたコミット」であって、原因ではありません

`git bisect` が答えるのは、**どのコミットから壊れたか**までです。
そのコミットの中身のどこが原因かは、`git show` や `git diff` で読んで探します。

とはいえ、60 個の中から 1 個に絞れていれば、読む量はまるで違います。
「どこを読めばいいか」が分かっているのと、いないのとの差です。

## 本物との違い

本物には `git bisect run <コマンド>` があります。
判定を自分で打つ代わりに、テストを走らせて自動で good / bad を決めるものです。
このサイトには**入っていません** ― `git bisect run` を打つと断られます。
走らせるテストが無いので、置いても意味が出ないためです。

考え方は同じで、**答えを人が打つか、コマンドが打つか**が違うだけです。
