# cherry-pick ― 1 つだけ摘む

「あの枝の、あのコミットだけが欲しい」

枝ごと取り込む（[merge](/docs/three-way)）ほどではない。
枝ごと引っ越す（[rebase](/docs/rebase)）のも違う。
1 つだけ持ってきたい。そのためのコマンドです。

```bash
git cherry-pick a1b2c3d
```

```
        (X) ── (Y) ← feature
       /
── (A) ── (B) ← main
```

`main` に立って `Y` を cherry-pick すると、

```
        (X) ── (Y) ← feature
       /
── (A) ── (B) ── (Y') ← main
```

`Y'` ができました。中身は `Y` と同じですが、**id が違います**。

## コピーであって、移動ではありません

ここが肝心です。`Y` は `feature` に残っています。消えも動きもしません。

つまり cherry-pick のあとは、**同じ中身が 2 か所にある**状態になります。

これは意図した結果でもあり、あとで困る種でもあります。
あとから `feature` を `main` にマージすると、Git は同じ変更を 2 回見ることになります。
たいていはうまく処理されますが、コンフリクトになることもあります。

## id が変わる理由

コミットの id は、中身だけでなく**親**からも計算されます。
`Y` の親は `X`、`Y'` の親は `B`。親が違うので、別のコミットです。

同じ理屈が rebase にも当てはまります。
実のところ rebase は、**複数のコミットを順に cherry-pick している**ようなものです。

| コマンド | 何を持ってくるか |
| --- | --- |
| `cherry-pick` | 指定した 1 つ（または複数） |
| `rebase` | 枝が持っているコミットを全部 |

## 使いどころ

いちばん多いのは、**修正だけを別の枝へ持っていく**場面です。

開発中の枝でバグを直した。その修正はリリース版にも要る。
でも開発中の機能はまだ入れたくない。そんなときに、修正のコミットだけを摘みます。

逆に、cherry-pick が増えてきたら立ち止まったほうがいいかもしれません。
同じ変更が履歴のあちこちに散らばると、何がどこに入っているのか追えなくなります。

## 複数まとめて

範囲でも指定できます。

```bash
git cherry-pick a1b2c3d e4f5g6h      # 2 つ
git cherry-pick main..feature        # main に無いものを全部
```

ただし `..` の書き方は、このサイトでは**扱っていません**。
上の 2 行目を打つと断られます。複数まとめてなら、1 行目のように id を並べてください。

2 つ目は、やっていることが rebase にかなり近づきます。
