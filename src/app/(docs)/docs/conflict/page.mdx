# コンフリクト ― 止まるだけで、壊れない

コンフリクトが怖いのは、**何が起きたのか分からないまま止まる**からだと思います。
先に結論を書いておきます。

**何も壊れていません。**

- コミットは 1 つも増えていません
- 枝もどれも動いていません
- HEAD もそのままです

増えたのは「マージの途中である」という印だけです。

## いつ起きるのか

[3-way マージ](/docs/three-way)のうち、**両側が同じ行を変えていた**ときだけです。

分岐点（base）と比べて、`ours` も `theirs` も変わっている。
どちらを残すべきか、Git には判断材料がありません。
だから手を止めて、こちらに判断を渡してきます。

大事なのは、判定が**ファイル単位ではなく行単位**だということです。

| 両側の触り方 | 結果 |
| --- | --- |
| 別々のファイルを触った | 黙って両方入る |
| 同じファイルの、**離れた行**を触った | 黙って両方入る |
| 片側だけが触った | 触ったほうが入る |
| 同じファイルの、**同じ行**を違う中身にした | ここで初めて止まる |
| 触った行が**隣り合っていた** | 別の行でも止まる |
| 両側が**同じ場所に**行を足した | 順番を決められないので止まる |

つまり、ぶつかるほうが例外です。
同じファイルを二人で触っただけでは、たいてい何も起きません。

### 「離れた」とは、どれくらい離れていればよいか

**変えていない行が、あいだに 1 行でも残っていれば足ります。**

```
a       ← 変えていない
b幹     ← こちらが変えた
c       ← 変えていない（これが 1 行あれば足りる）
d枝     ← 向こうが変えた
e
```

この `c` が無くなって `b` と `c` を両側が別々に変えると、
別の行を触っているのに止まります。
Git は変更を**かたまり**で見ていて、地続きのかたまりは切り分けられないからです。

同じ理由で、両側が末尾に 1 行ずつ足した場合も止まります。
行としては別々でも、**足す場所が同じ**なので、どちらを先にするかが決まりません。

### 手を動かして確かめる

このサイトなら、[サンドボックス](/sandbox)でこう打つと、止まらないほうを見られます。

```bash run
touch v.txt 1行目
git add .
git commit -m "根"

git switch -c feature
append v.txt 枝が足した行      # 末尾に足す
git add .
git commit -m "枝"

git switch main
edit v.txt 幹が直した          # 1 行目を直す
git add .
git commit -m "幹"

git merge feature              # 止まらない。両方入る
```

`touch` で作ったファイルは 2 行あるので、1 行目と末尾のあいだに
変えていない行が 1 行残ります。だから切り分けられます。

`edit` の代わりに `append` を使うと、両側が末尾に足すことになって止まります。
その 1 文字違いで結果が変わるところが、この判定の勘所です。

## 目印が書き込まれます

止まると、Git はぶつかったファイルに**両方の案を並べて書き込みます**。

```
<<<<<<< HEAD
店頭のアレンジ（店長が生けた）
=======
店頭のアレンジ（春の花）
>>>>>>> spring
```

`<<<<<<<` から `=======` までが**こちら側**、
`=======` から `>>>>>>>` までが**向こう側**です。

ファイルが壊れたわけではありません。
「両方置いておくから、どちらを残すか決めて」と言われているだけです。

## 残す中身を決める

やり方は 3 つあります。

```bash
git checkout --ours vase.txt     # こちら側をまるごと残す
git checkout --theirs vase.txt   # 向こう側をまるごと残す
edit vase.txt <残したい中身>      # 自分で書く（本物ならエディタで開く）
```

`--ours` と `--theirs` は、目印ごと片側に置き換えます。
どちらでもない第三の案（両方を合わせたもの）にしたいときは、自分で書きます。

### rebase のときは、ours と theirs が入れ替わります

ここが rebase でいちばん事故が起きるところです。

| 止まった操作 | `--ours` は | `--theirs` は |
| --- | --- | --- |
| merge | いまいる枝（自分） | 取り込む枝（相手） |
| rebase / cherry-pick | **置き直す先**（`main` 側） | **いま当てているコミット**（自分の作業） |

理由はこうです。rebase は「`main` の上に、自分のコミットを 1 つずつ**取り込んで**いく」操作なので、
Git から見ると**自分のほうが「相手」**になります。

merge のつもりで `--ours` を打つと、自分のコミットの中身が丸ごと消えます。
しかも黙って通るので、気づくのは何コミットも先です。

このサイトは目印にそのまま書き分けています ― 迷ったら、書いてあるほうを読んでください。

```
<<<<<<< 積む先        ← --ours（main 側）
>>>>>>> 枝の変更      ← --theirs（自分の作業）
```

**目印を消し忘れないでください。**
本物の Git は、`<<<<<<<` が残ったままでも `add` を通してしまいます。
その結果、目印の入ったファイルがそのままコミットされる ―
実務でいちばんよく見かける事故がこれです。
このサイトでは教材として、目印が残っていると `add` を断ります。

## 出口は 2 つだけです

```bash
# (1) 決着をつける
git add vase.txt         # 「もう見た。これで確定」と Git に伝える
git commit               # 親を 2 つ持つマージコミットができる

# (2) やめる
git merge --abort        # 始める前の状態にそのまま戻る
```

これだけです。

`--abort` があることを**先に**知っておくと、コンフリクトは怖くなくなります。
「詰んだら戻れる」と分かっていれば、`git merge` を気軽に打てます。

## 後始末に専用のコマンドはありません

意外に思われるところですが、コンフリクトを解決する専用のコマンドはありません。
使うのは、いつもの `add` と `commit` です。

`add` はふだん「作業ディレクトリからステージへ運ぶ係」ですが、
マージの途中では「**このファイルは決着がついた**」という印にもなります。
残りが 0 になると、`commit` が通るようになります。

`commit` も、いつもの `commit` です。
違うのは、できあがるコミットの親が 2 つになることだけ。
メッセージを省くと、Git が用意した既定文（"Merge branch 'feature'"）が使われます。

## 止まっている間にできること

本物の Git は、コンフリクト中に多くの操作を断ります。
決着していない状態の上に別の操作を重ねると、収拾がつかなくなるからです。

このサイトも同じで、通すのはこれだけです。

| 通るもの | なぜ |
| --- | --- |
| `git status` | いまどうなっているかを確かめる |
| `git diff` | 書き込まれた目印と、両側の中身を読む |
| `git log` / `git reflog` | 履歴を見て、どちらを残すか決める |
| `git checkout --ours` / `--theirs` | 片側をまるごと選ぶ |
| `edit` | 自分で中身を書く |
| `git add` | 決着をつけた印 |
| `git commit` | 決着を確定する |
| `git merge --abort` | やめる |

迷ったら `git status` です。残りのファイルと、そこから進む 2 通りの道を、そのつど教えてくれます。

## 止まるのは merge だけではありません

実務でいちばん痛いのは、じつは merge ではなく **rebase** の途中で止まることです。

[rebase](/docs/rebase) はコミットを**1 つずつ**当て直します。
だから、ぶつかるたびに手が止まります。5 件置き直すなら、最悪 5 回止まります。

続け方も、やめ方も、3 つとも違います。

| 止まったもの | 続ける | やめる |
| --- | --- | --- |
| merge | `git commit`（`git merge --continue` でも同じ） | `git merge --abort` |
| rebase | `git rebase --continue` | `git rebase --abort` |
| cherry-pick | `git cherry-pick --continue` | `git cherry-pick --abort` |

merge だけ「そのまま `git commit` でよい」のは、**続きが無い**からです。
merge は 1 回で終わる操作なので、決着をつけたらコミットすれば済みます。
`git merge --continue` も同じことをします ― 呼び名が 2 つあるだけです。

rebase と cherry-pick は違います。「まだ残りがある」ことを Git 側が覚えていて、
`--continue` はそれを先へ進めるためのコマンドです。
だからこの 2 つでは `git commit` では終われません。

どれで止まっているかは `git status` が教えてくれます。

### 決着のつけ方が、次の止まり方を変えます

rebase で 2 件を置き直すとき、1 件目で**向こう側**を選んだか**こちら側**を選んだかで、
2 件目がぶつかるかどうかが変わります。

向こう側（＝置き直す元の中身）を選ぶと、2 件目から見て「片側しか変えていない」形になるので、
たいてい黙って通ります。こちら側を残すと、2 件目は 3 つの版がすべて違う形になり、また止まります。

これは覚えることではなく、**3 つの版を比べているだけ**だと分かっていれば導けます。
迷ったら、いま何と何が比べられているのかに戻ってください。

## やめても壊れません

`--abort` は、ファイルの中身まで含めて始める前に戻します。
書き込まれた目印も残りません。

rebase を途中でやめた場合、そこまでに作ったコピーは
**どの枝からも辿れない場所に残ります**。消えたわけではないので、
[reflog](/docs/reflog) から拾い直せます。
