# コンフリクト ― 止まるだけで、壊れない

コンフリクトが怖いのは、**何が起きたのか分からないまま止まる**からだと思います。
先に結論を書いておきます。

**何も壊れていません。**

- コミットは 1 つも増えていません
- 枝もどれも動いていません
- HEAD もそのままです

増えたのは「マージの途中である」という印だけです。

## いつ起きるのか

[3-way マージ](/docs/three-way)のうち、**両側が同じファイルを変えていた**ときだけです。

分岐点（base）と比べて、`ours` も `theirs` も変わっている。
どちらを残すべきか、Git には判断材料がありません。
だから手を止めて、こちらに判断を渡してきます。

逆に言えば、**別々のファイルを触っている限り、コンフリクトは起きません**。
両側が同じファイルを変えていても、離れた行なら本物の Git は自動で両方を取り込みます。

## 出口は 2 つだけです

```bash
# (1) 決着をつける
git add a.txt            # 「もう見た。これで確定」と Git に伝える
git commit               # 親を 2 つ持つマージコミットができる

# (2) やめる
git merge --abort        # 始める前の状態にそのまま戻る
```

これだけです。

`--abort` があることを**先に**知っておくと、コンフリクトは怖くなくなります。
「詰んだら戻れる」と分かっていれば、とりあえず `git merge` を打ってみられます。

## 後始末に専用のコマンドはありません

意外に思われるところですが、コンフリクトを解決する専用のコマンドはありません。
使うのは、いつもの `add` と `commit` です。

`add` はふだん「作業ディレクトリからステージへ運ぶ係」ですが、
マージの途中では「**このファイルは決着がついた**」という印にもなります。
残りが 0 になると、`commit` が通るようになります。

`commit` も、いつもの `commit` です。
違うのは、できあがるコミットの親が 2 つになることだけ。
メッセージを省くと、Git が用意した既定文（`Merge feature into main`）が使われます。

## 止まっている間にできること

本物の Git は、コンフリクト中に多くの操作を断ります。
決着していない状態の上に別の操作を重ねると、収拾がつかなくなるからです。

このサイトも同じで、通すのはこれだけです。

| 通るもの | なぜ |
| --- | --- |
| `git status` | いまどうなっているかを確かめる |
| `git log` / `git reflog` | 履歴を見て、どちらを残すか決める |
| `git add` | 決着をつけた印 |
| `git commit` | 決着を確定する |
| `git merge --abort` | やめる |

迷ったら `git status` です。残りのファイルと、そこから進む 2 通りの道を、そのつど教えてくれます。

## 本物の Git との違い

本物の Git は、コンフリクトしたファイルの中に目印を書き込みます。

```
<<<<<<< HEAD
こちら側の行
=======
相手側の行
>>>>>>> feature
```

この目印を消して、残したい形に整えるのが「決着をつける」の中身です。

このサイトはファイルの中身を持たないので、目印は出しません。
判定も行単位ではなく、**分かれたあと両側が同じファイルを変えたか**で見ています。
起きる理由と、そこから抜ける手順は同じです。
