# fast-forward マージ

`git merge` を打ったのに、マージコミットができない。
最初に出会う「思っていたのと違う」は、たいていこれです。

理由は単純で、**分かれていないから**です。

## 結末は 3 つ、決めるのは位置関係だけ

`git merge <相手>` の結末は 3 通りしかありません。
そして、どれになるかは**2 つのコミットの位置関係だけ**で決まります。

| 位置関係 | 何が起きるか |
| --- | --- |
| 相手がすでに自分の祖先 | 取り込むものが無い。グラフは変わらない |
| 自分が相手の祖先 | **fast-forward**。コミットは増えず、名前が前へ滑るだけ |
| どちらでもない | **3-way**。親を 2 つ持つマージコミットが生まれる |

オプションでも設定でもなく、形だけで決まります。

## fast-forward の形

```
── (A) ── (B) ← main
            \
             (C) ── (D) ← feature
```

……という図は、実は正しくありません。`main` は `D` の祖先なので、実態はこうです。

```
── (A) ── (B) ── (C) ── (D)
           ↑              ↑
          main         feature
```

1 本の道です。`main` が後ろにいるだけ。
ここで `main` に立って `git merge feature` を打つと、Git はこう考えます。

> 合流点を作る意味がない。`main` を `D` まで滑らせれば済む。

```
── (A) ── (B) ── (C) ── (D)
                         ↑
                    main, feature
```

コミットは 1 つも増えていません。名札が前へ動いただけです。
これが fast-forward（早送り）です。

## なぜ合流点を作らないのか

作っても構いませんが、意味のない親が 1 つ増えます。
「A と B を合わせた結果が C です」と書き残すのがマージコミットなのに、
合わせるものが片方しか無いなら、記録する価値がありません。

履歴を読む人にとっても、意味のない合流点は雑音です。

## 明示的に合流点を作りたいとき

チームによっては「機能を取り込んだ事実を履歴に残したい」ことがあります。
本物の Git では `--no-ff` を付けると、fast-forward できる場合でもマージコミットを作ります。

```bash
git merge --no-ff feature
```

このサイトでは扱っていませんが、`--no-ff` で作られたコミットが履歴にたくさん並んでいるリポジトリは、
この方針を採っています。

## 取り込むものが無いとき

相手がすでに自分の祖先なら、Git は何もしません。

```
Already up to date.
```

このサイトでは「すでに取り込まれています」と出ます。
失敗ではなく、やることが無いという報告です。
