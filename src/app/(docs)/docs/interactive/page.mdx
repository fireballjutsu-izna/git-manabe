# 対話的 rebase ― まとめる・落とす・並べ替える

`git rebase -i` は、[rebase](/docs/rebase) に**計画を挟んだもの**です。

素の rebase は、並んでいるコミットをそのまま 1 つずつ当て直します。
`-i` は、当てる前に「どう当てるか」を書き換えさせてくれます。

## 打っても、まだ何も起きません

ここがいちばん大事なところです。

```bash
git rebase -i main
```

これを打つと、本物の Git は**エディタを開くだけ**です。
履歴は 1 ミリも動いていません。開くのはこういうテキストです。

```
pick   a1b2c3d  ラッピングを直した
pick   e4f5g6h  typo
pick   i7j8k9l  デバッグ用のログ
```

これが **todo リスト**です。上が古い順に並んでいます。
行を書き換えて、**エディタを閉じたときに**初めて実行が始まります。

このサイトにはエディタが無いので、同じ表をパネルとして出します。
ボタンは `todo` コマンドを打っているだけなので、
打った内容はターミナルに残り、「1 手戻す」も効きます。

## 4 つの指定

| 指定 | 何をするか |
| --- | --- |
| `pick` | そのまま積む（既定） |
| `squash` | **1 つ上のコミットにまとめる** |
| `reword` | 中身はそのまま、メッセージだけ書き換える |
| `drop` | 落とす |

`squash` は「1 つ上」にまとめるので、**1 行目には付けられません**。
上にまとめる相手がいないからです。

行の順番も変えられます。並べ替えれば、その順に積み直されます。

## いちばん使うのは squash です

実務では、こういう履歴が普通にできます。

```
pick   a1b2c3d  ラッピングを直した
pick   e4f5g6h  typo
pick   i7j8k9l  typo 直し忘れ
```

やったことは 1 つなのに、コミットが 3 つ。
レビューする人は 3 回読むことになりますし、あとで `revert` したいときも 3 回打つことになります。

```
pick   a1b2c3d  ラッピングを直した
squash e4f5g6h  typo
squash i7j8k9l  typo 直し忘れ
```

こうすると、**1 つのコミットになります**。中身は 3 つぶん全部入ったままです。

「きれいにする」のが目的ではありません。
**あとで読む人が、1 つの変更を 1 か所で読めるようにする**のが目的です。

## 途中で止まることがあります

1 つずつ当て直すので、素の rebase と同じくぶつかると止まります。
止まり方も、抜け方も同じです。

```bash
git checkout --theirs app.ts   # 残す中身を決めて
git add app.ts                 # 決着をつけて
git rebase --continue          # 計画の続きへ戻る
```

`squash` の途中で止まっても、決着をつけた中身は**同じ塊に足されます**。
まとめる計画が、途中で崩れることはありません。

やめるなら `git rebase --abort` です。
計画を立てている段階（実行前）なら、そもそも何も起きていないので、消えるのは計画だけです。

## 送ったあとに書き換えたら ― force-with-lease

> ここから先は `push` と「向こうのリポジトリ」の話が出てきます。
> まだ読んでいなければ、[リモートの記事](/docs/remote)を先に読んでも構いません。
> 要点だけ言うと、`push` は**自分のコミットを向こうへ配る**操作です。

自分の枝を `push` したあとで `-i` をかけると、次の `push` は**断られます**。

```
origin の feature には、あなたが持っていないコミットがあります。
```

向こうにあるのは**書き換える前の版**で、こちらの新しいコミットからは辿れません。
Git から見れば「知らないコミットがある」ので、同じ言い方になります。

ここで `git pull` してはいけません。捨てたはずの古い版が、また入ってきます。
自分で書き換えたのだから、押し出します。

```bash
git push --force-with-lease origin feature
```

`--force` ではなく `--force-with-lease` を使ってください。違いはここです。

| 指定 | 上書きの条件 |
| --- | --- |
| `--force` | 問答無用で上書きする |
| `--force-with-lease` | **自分が最後に見たときから向こうが動いていなければ**上書きする |

間に誰かが `push` していた場合、`--force` はその人の作業を消します。
`--force-with-lease` は、そこで止まってくれます。
止まったら `git fetch` で何が起きたか確かめてから決めます。

「lease（借り）」という名前は、**自分が見た向こうの位置を借りたまま**にしておいて、
返すときに変わっていないかを照合する、という意味です。

## 書き換えてよい枝、だめな枝

`-i` は履歴を**書き換えます**。id が全部変わるので、
その枝を土台にしている人がいると、その人の手元と食い違います。

線は「`push` したかどうか」ではありません。**他の人がその枝を当てにしているか**です。

| 枝の状態 | 書き換えてよいか |
| --- | --- |
| まだ `push` していない | 好きに整えてよい |
| `push` 済みの、自分の作業枝（レビュー中の枝など） | 整えてよい。`--force-with-lease` で押し出す |
| `main` や `develop` など、みんなが `pull` する枝 | **絶対に書き換えない**。直すなら [revert](/docs/revert) |

真ん中の行が、実務でいちばん多い場面です。
レビューの指摘を直すたびに `fix typo` を積むより、
`-i` でまとめてから押し出すほうが、読む人の手間が減ります。
上の「送ったあとに書き換えたら」で見たのが、まさにこれです。

危ないのは 3 行目だけです。**その枝から枝を切っている人がいないか**が判断の分かれ目で、
分からなければ聞くのがいちばん早い。
