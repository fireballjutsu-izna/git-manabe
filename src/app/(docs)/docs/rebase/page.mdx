# rebase ― 土台を置き直す

`rebase` は「履歴をきれいにするもの」と説明されがちですが、
実際にやっていることはもっと具体的です。

**自分のコミットを、別の場所へコピーし直します。**

```bash
git switch feature
git rebase main          # feature のコミットを main の先端の上へ置き直す
```

```
        (X) ── (Y) ← feature
       /
── (A) ── (B) ← main
```

これが、こうなります。

```
        (X) ── (Y)          ← 誰も指していない
       /
── (A) ── (B) ── (X') ── (Y') ← feature
```

## merge との違いは 1 点です

| コマンド | 何をするか | 元のコミットは | 履歴は |
| --- | --- | --- | --- |
| `merge` | 2 つの流れを**合流**させる | そのまま残る | 増える（合流点が 1 つ） |
| `rebase` | 自分のコミットを**コピーし直す** | 指されなくなる | **作り直される（id が変わる）** |

`merge` は木に枝を足します。`rebase` は枝を生やす場所を変えます。

## コピー元は消えません

上の図の `X` と `Y` は、そこにあります。
**どの枝からも指されなくなっただけ**です。

このサイトでは、そういうコミットを破線・薄い色で描き続けます。
「作り直された」ことが目で見えるようにするためです。

指す名前が無いので、放っておけばいずれ Git のお掃除（gc）で本当に消えます。
それまでは [reflog](/docs/reflog) から拾えます。

## 共有済みの履歴には使えません

id が変わるということは、**他の人が持っている履歴と食い違う**ということです。

あなたの手元では `X'` になったコミットが、同僚の手元では `X` のまま。
Git から見ると、これは別のコミットです。
同僚が次に pull すると、同じ変更が 2 つ並んだ奇妙な履歴ができあがります。

> 自分しか触っていない枝なら rebase してよい。
> push して他の人が見た枝は、rebase しない。

覚え方はこれで足ります。

## それでも rebase を使う理由

`merge` を繰り返すと、履歴に合流点がたくさん並びます。
何が起きたかは正確に残りますが、読むのは大変です。

`rebase` すると、枝の作業が `main` の先端から一直線に伸びた形になります。
「この機能のために、この 3 つのコミットを積んだ」と読めるので、
あとからレビューする人にとっては分かりやすくなります。

正確さを取るか、読みやすさを取るか。チームの方針で決まる話です。

## このサイトでの簡略化

- 作業中の変更があっても実行できます。本物の Git は、そのままだと断ります
- マージコミットは置き直しません（本物の Git も既定では落とします）
- 対話的 rebase（`-i`）は扱っていません。コミットの並べ替えや、まとめ（squash）ができるものです
