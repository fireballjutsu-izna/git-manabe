# rebase ― 土台を置き直す

`rebase` は「履歴をきれいにするもの」と説明されがちですが、
実際にやっていることはもっと具体的です。

**自分のコミットを、別の場所へコピーし直します。**

```bash
git switch feature
git rebase main          # feature のコミットを main の先端の上へ置き直す
```

```
        (X) ── (Y) ← feature
       /
── (A) ── (B) ← main
```

これが、こうなります。

```
        (X) ── (Y)          ← 誰も指していない
       /
── (A) ── (B) ── (X') ── (Y') ← feature
```

## merge との違いは 1 点です

| コマンド | 何をするか | 元のコミットは | 履歴は |
| --- | --- | --- | --- |
| `merge` | 2 つの流れを**合流**させる | そのまま残る | 増える（合流点が 1 つ） |
| `rebase` | 自分のコミットを**コピーし直す** | 指されなくなる | **作り直される（id が変わる）** |

`merge` は木に枝を足します。`rebase` は枝を生やす場所を変えます。

## コピー元は消えません

上の図の `X` と `Y` は、そこにあります。
**どの枝からも指されなくなっただけ**です。

このサイトでは、そういうコミットを破線・薄い色で描き続けます。
「作り直された」ことが目で見えるようにするためです。

指す名前が無いので、放っておけばいずれ Git のお掃除（gc）で本当に消えます。
それまでは [reflog](/docs/reflog) から拾えます。

## 共有済みの履歴には使えません

id が変わるということは、**他の人が持っている履歴と食い違う**ということです。

あなたの手元では `X'` になったコミットが、同僚の手元では `X` のまま。
Git から見ると、これは別のコミットです。
同僚が次に pull すると、同じ変更が 2 つ並んだ奇妙な履歴ができあがります。

> 他の人が土台にしていない枝なら、rebase してよい。
> みんなが pull する枝（main など）は、rebase しない。

線は「`push` したかどうか」ではありません。
`push` 済みでも、自分の作業枝を整えて `--force-with-lease` で押し出すのは、
実務でごく普通にやることです。詳しくは[対話的 rebase](/docs/interactive) に書きました。

## それでも rebase を使う理由

`merge` を繰り返すと、履歴に合流点がたくさん並びます。
何が起きたかは正確に残りますが、読むのは大変です。

`rebase` すると、枝の作業が `main` の先端から一直線に伸びた形になります。
「この機能のために、この 3 つのコミットを積んだ」と読めるので、
あとからレビューする人にとっては分かりやすくなります。

正確さを取るか、読みやすさを取るか。チームの方針で決まる話です。

## 1 つずつ当てるので、何度も止まります

rebase のいちばん厄介なところは、ここです。

merge は 1 回で終わります。ぶつかっても、止まるのは 1 回だけ。
rebase は**コミットを 1 つずつ当て直す**ので、5 件置き直すなら最悪 5 回止まります。

```bash
git rebase main
# → 1 件目でぶつかって止まる

git checkout --theirs app.ts   # 残す中身を決めて
git add app.ts                 # 決着をつけて
git rebase --continue          # 次へ進む
# → 2 件目でまた止まる…
```

`git commit` ではなく `git rebase --continue` なのが要点です。
Git は「まだ残りがある」ことを覚えていて、`--continue` はそれを先へ進めるためのコマンドです。
merge が `git commit` だけで終われるのは、続きが無いからにすぎません（`git merge --continue` もあります）。

やめたくなったら `git rebase --abort` で、置き直す前にまるごと戻せます。
途中まで作ったコピーは、どの枝からも辿れない場所に残るだけで、消えません。

詳しくは[コンフリクト](/docs/conflict)の記事に書いてあります。

## このサイトでの簡略化

- マージコミットは置き直しません（本物の Git も既定では落とします）

対話的 rebase（`-i`）は扱っています。コミットをまとめたり、落としたり、並べ替えたりできる
`rebase` で、実務ではこちらのほうがよく使います。
