# revert ― 消さずに打ち消す

「あのコミット、無かったことにしたい」

方法は 2 つあります。[reset](/docs/reset-modes) と `revert` です。
やりたいことは同じに見えて、履歴に対する態度がまるで違います。

| コマンド | 履歴は | 元のコミットは |
| --- | --- | --- |
| `reset` | **後ろへ動く**（書き換え） | 残るが、指されなくなる |
| `revert` | **増える**（打ち消しが 1 つ） | そのまま残る |

## revert は前に足します

```bash
git revert HEAD
```

```
── (A) ── (B) ── (C) ── (C') ← main
```

`C'` が新しくできたコミットです。中身は `C` の**逆向きの変更**。
`C` が「この行を足した」なら、`C'` は「この行を消した」になります。

結果として、ファイルの中身は `B` のときと同じに戻ります。
でも履歴には `C` も `C'` も残っています。

「取り消した」という事実まで含めて、記録に残るわけです。

## 共有済みの履歴に使えるのはこちらだけ

これが `revert` の存在理由です。

`reset` は枝を後ろへ動かします。すでに push して他の人が持っているコミットを
消してしまうと、向こうの履歴と食い違い、次の push が断られます。
無理に通すと、相手の手元が壊れます。

`revert` は**足すだけ**なので、誰の履歴とも食い違いません。
ふつうに push できます。

> 共有した履歴は書き換えない。取り消したいなら、打ち消しを足す。

## マージを revert するとき

マージコミットには親が 2 つあるので、「どちらへ戻すのか」を伝える必要があります。
本物の Git では `-m 1` のように第一親を指定します。

```bash
git revert -m 1 <マージコミット>
```

マージコミットの revert は、このサイトでは**扱っていません**。
上の形を打つと断られます。ここで打ち消せるのは、親が 1 つのコミットだけです。

マージを revert したあとに同じ枝をもう一度マージしても
何も起きない、という有名な落とし穴があります。
Git から見ると「そのマージはすでに取り込み済み」だからです。

## 打ち消しを打ち消せます

`revert` でできたコミットも、ただのコミットです。
`git revert` をもう一度打てば、打ち消しを打ち消せます。

```
── (C) ── (C') ── (C'') ← main
```

`C''` は `C` と同じ中身になります。履歴は 3 つとも残ります。
遠回りに見えますが、共有された履歴の上ではこれがいちばん安全な道です。
