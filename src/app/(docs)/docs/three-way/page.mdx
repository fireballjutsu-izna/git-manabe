# 3-way マージ

両側がそれぞれ進んでいるとき、名前を滑らせるだけでは済みません。
どちらの変更も残したいので、**合流点**を作ります。

```
        (C) ← main
       /
── (A) ── (B) ← feature
```

`main` に立って `git merge feature` を打つと、こうなります。

```
        (C) ─── (M) ← main
       /       /
── (A) ── (B) ─┘  ← feature
```

`M` が新しくできたマージコミットです。**親が 2 つ**あります。

## なぜ 3-way と呼ぶのか

Git が見ているのは 3 つのコミットだからです。

| 呼び名 | 何か |
| --- | --- |
| ours | 自分の先端（`C`） |
| theirs | 相手の先端（`B`） |
| base | **分岐点**（`A`） |

分岐点は、両側から辿れる共通の祖先のうち、いちばん新しいものです（merge base）。

なぜ分岐点が要るのか。`ours` と `theirs` を並べただけでは、
「変えたのか、変えなかったのか」が分からないからです。

たとえば `a.txt` が `ours` と `theirs` で違っていたとします。
どちらが変えたのでしょうか。両方かもしれません。片方だけかもしれません。
`base` と比べて初めて、それが判ります。

- `base` と `ours` が同じ → 変えたのは `theirs`。相手の側を採る
- `base` と `theirs` が同じ → 変えたのは `ours`。自分の側を採る
- **どちらも `base` と違う** → 両方が変えた。Git には決められない ＝ [コンフリクト](/docs/conflict)

3 つ目を見ているから 3-way です。

## 動くのは片方だけです

マージしても、動くのは**自分がいる枝だけ**です。

```
        (C) ─── (M) ← main, HEAD
       /       /
── (A) ── (B) ─┘  ← feature   ← ここは動かない
```

`feature` は `B` を指したままです。
「取り込む」は一方通行で、相手の枝には何もしません。

用が済んだ `feature` を消したくなったら、`git branch -d feature` です。
コミットは消えません。名札が外れるだけで、`M` から辿れる位置にあり続けます。

## グラフでの見え方

このサイトでは、マージコミットを**二重丸**で描いています。
線が 2 本入ってくる点は、履歴の中でここだけなので、目印になります。

`git log --graph` でも、この点だけ枝が合流して見えます。

## 順番は結果に関係しません

`main` で `feature` を取り込むのと、`feature` で `main` を取り込むのとでは、
できあがるコミットの中身は同じです。違うのは、

- どちらの枝が動くか
- マージコミットの**第一親**がどちらになるか

の 2 点だけです。第一親は `HEAD~1` が指す先を決めるので、
あとから履歴を辿るときに効いてきます。
