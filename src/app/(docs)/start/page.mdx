# はじめに

このサイトの Git は、**本物の Git を動かしているわけではありません**。
コミット・ブランチ・HEAD・ステージを、教育用に単純化したデータとして持ち、
コマンドを「状態 → 新しい状態」の計算として実行しています。

そうしている理由は 1 つで、**いちばん図で見たい操作ほど、ブラウザで動く本物の Git が苦手**だからです。
たとえば rebase・reflog・コンフリクトの解決は、
純 JavaScript 実装の isomorphic-git には入っていないか、途中で中断してしまいます。
このサイトはそこを見せたいので、エンジンを自分で書いています。

## 最初に打つ並び

```bash
git init                  # まだコミットが 1 つも無いリポジトリができる
touch hello.txt           # 作業ディレクトリに変更を作る（Git のコマンドではありません）
git add hello.txt         # 作業ディレクトリ → ステージ
git commit -m "はじめの一歩"  # ステージ → リポジトリ。ここで main が生まれる
```

`git init` の直後は、`main` という枝は**まだ存在しません**。
HEAD は「これから作られる `main`」を指していて、最初の `commit` がその枝を生みます。
本物の Git と同じ挙動で、ここを省略すると後の detached HEAD の話が通じなくなるので、そのまま再現しています。

## 枝を分ける

```bash
git branch feature        # いまのコミットに feature という名前を付ける（HEAD は動かない）
git switch feature        # HEAD を feature へ移す
git commit -m "枝の上で作業"  # feature だけが伸びて、main は置いていかれる
```

## 3 つの領域

Git が値を持つ場所は 3 つあります。サンドボックスでは常に横に出しています。

| 領域 | 何が入っているか | 動かすコマンド |
| --- | --- | --- |
| 作業ディレクトリ | 編集しただけで、まだ Git に渡していない変更 | `touch` / `edit` |
| ステージ (index) | 次のコミットに含めると決めた変更 | `git add` |
| リポジトリ | コミットとして確定した履歴 | `git commit` |

コマンドを打つと、**書き換わった領域だけが一瞬光ります**。
どのコマンドがどこを触ったのかは、それを見るのがいちばん早いです。

## 枝を 1 つに戻す

```bash
git switch main
git merge feature        # feature を main に取り込む
```

結末は 3 つあり、どれになるかは**2 つのコミットの位置関係だけ**で決まります。

| 位置関係 | 何が起きるか |
| --- | --- |
| 相手がすでに自分の祖先 | 取り込むものが無い。グラフは変わらない |
| 自分が相手の祖先 | **fast-forward**。コミットは増えず、名前が前へ滑るだけ |
| どちらでもない（分かれている） | **3-way**。親を 2 つ持つマージコミットが生まれる |

「マージしたのにマージコミットができない」と戸惑うのは、たいてい fast-forward です。
分かれていないのだから、合流点を作る意味がありません。

3-way のときだけ、グラフのその点に**線が 2 本入ってきます**。サイト上では二重丸で描いています。

## 巻き戻す ― reset の 3 つのモード

```bash
git reset --soft  HEAD~1   # 枝だけ戻す
git reset --mixed HEAD~1   # 枝を戻し、ステージも空にする（既定）
git reset --hard  HEAD~1   # 枝を戻し、ステージも作業ディレクトリも空にする
```

名前を共有している**3 つの別コマンド**だと思うのが早いです。
**どのモードでも枝は同じだけ動きます。**違うのは、取り消したコミットに入っていた変更を
どこまで戻すか、それだけです。

| | 枝 (HEAD) | ステージ | 作業ディレクトリ | 取り消した変更は |
| --- | --- | --- | --- | --- |
| `--soft` | 動く | 残す | 残す | ステージに積まれたまま |
| `--mixed` | 動く | 消す | 残す | 未ステージの変更に落ちる |
| `--hard` | 動く | 消す | 消す | 消える |

表を読むより、サンドボックスで 3 回打ち分けて**3 領域パネルのどこが光るか**を見るのが早いです。
`--soft` ではステージだけ、`--mixed` と `--hard` では両方が光ります。

`--hard` で消した作業中の変更は、reflog を使っても戻せません。
一方で、**取り消したコミット自体は消えていません**。HEAD から辿れなくなっただけです。

`HEAD~1` は「いまの場所から 1 代さかのぼる」という意味で、`HEAD^` と同じです。
`HEAD~2` なら 2 代です。

## 作り直す ― rebase

```bash
git switch feature
git rebase main          # feature のコミットを main の先端の上へ置き直す
```

merge との違いは 1 点に尽きます。

- **merge** は 2 つの流れを**合流**させます。元のコミットはそのままで、合流点が 1 つ増えます
- **rebase** は自分のコミットを 1 つずつ**コピーし直します**。id が変わる ＝ 別のコミットになります

コピー元は消えません。**どの枝からも指されなくなるだけ**です。
サイトでは、そういうコミットを破線・薄い色で描き続けます。
「作り直された」ことが目で見えるようにするためです。

id が変わるということは、他の人が持っている履歴と食い違うということでもあります。
だから rebase は**共有済みの履歴には使えません**。

## 摘む ― cherry-pick

```bash
git cherry-pick a1b2c3d
```

rebase が枝ごと引っ越すのに対し、こちらは 1 つだけ摘んできます。
やはりコピーなので id は変わり、元は元の場所に残ります。同じ中身が 2 か所にある状態になります。

## 打ち消す ― revert

```bash
git revert HEAD
```

reset との違いがここの要点です。

- **reset** は枝を後ろへ動かします。履歴そのものを書き換えます
- **revert** は履歴を 1 つも消さず、**逆向きの変更を前に足します**

他の人と共有した履歴を直すときは、後者しか使えません。

## 脇へどける ― stash

```bash
git stash               # 作業ディレクトリとステージを空にして、脇へ
git stash list
git stash pop           # 戻す
```

このサイトで**唯一、グラフが一切変わらない**コマンドです。
コミットを 1 つも作らず、動くのは 3 領域だけ。履歴には何の跡も残りません。

退避中は 3 領域パネルの下に一覧が出ます。コミットではないので、グラフには現れません。

## 5 つを並べると

| | 元のコミットは | 履歴は | 共有済みの履歴に使えるか |
| --- | --- | --- | --- |
| `merge` | 残る | 増える（合流点が 1 つ） | 使える |
| `rebase` | 残るが、指されなくなる | **作り直される（id が変わる）** | 使えない |
| `cherry-pick` | 残る | 増える（コピーが 1 つ） | 使える |
| `revert` | 残る | 増える（打ち消しが 1 つ） | 使える |
| `reset` | 残るが、指されなくなる | **後ろへ動く** | 使えない |

`stash` だけは履歴に触れないので、この表には入りません。

## やらかしても戻れる ― reflog

ここまでで、コミットをどこからも辿れなくする方法が 2 つ出てきました。
`reset --hard` と `rebase` です。どちらも**コミットを消してはいません**。
指す名前が無くなっただけで、実体はそこにあります。

その実体に届く最後の道が `git reflog` です。

```bash
git reset --hard HEAD~1        # しまった、1 つ消してしまった
git reflog                     # HEAD が通ってきた道が、新しい順に出る
```

```
b1c2d3e HEAD@{0}: reset --hard: HEAD~1 へ戻す
a9f8e7d HEAD@{1}: commit: 三つ目          ← いま辿れません
b1c2d3e HEAD@{2}: commit: 二つ目
```

`a9f8e7d` が、失くしたコミットです。拾い方は 2 つあります。

```bash
git reset --hard a9f8e7d        # そこまで丸ごと戻す
git switch -c 救出 a9f8e7d      # いまの場所は残したまま、枝を生やして拾う
```

後者のほうが安全です。いまの状態を壊さずに済みます。

### `HEAD@{1}` と `HEAD~1` は別物です

紛らわしいのですが、意味がまったく違います。

| | 何をさかのぼるか | 行き先 |
| --- | --- | --- |
| `HEAD~1` | **履歴**（親） | いまのコミットの親 |
| `HEAD@{1}` | **時間**（reflog） | 1 つ前に HEAD がいた場所 |

`reset --hard HEAD~1` を実行したあとだと、`HEAD~1` は「戻った先のさらに親」を指し、
`HEAD@{1}` は「reset する前にいた場所」＝ 失くしたコミットを指します。

### reflog は、あなたの手元にしかありません

枝やタグと違い、reflog は共有されません。他の人の reflog は見られませんし、
自分の reflog も push されません。**自分の操作の記録**だから、
自分がやらかしたことだけを救ってくれます。

なお `--hard` で消した**作業中の変更**（コミットしていなかったもの）は、
reflog にも残りません。こちらは本当に戻せません。

## もう 1 つのリポジトリ ― リモート

リモートは、**別の場所にあるもう 1 つのリポジトリ**です。
ここがいちばん大事な点で、**向こうのコミットは、fetch するまであなたのグラフに存在しません**。
見えていないのではなく、まだ持っていません。

```bash
git remote add origin <url>   # 名前を付けるだけ。まだ通信していない
git push origin main          # 送る
teammate 2                    # 誰かが向こうへ 2 つコミットした（このサイト独自）
```

`teammate` を打っても、**グラフは 1 ミリも動きません**。持っていないからです。
右のリモートパネルだけが「向こうに、まだ持っていないコミットがあります」と教えてくれます。

### fetch と pull の違いは 1 つだけ

```bash
git fetch origin              # 取ってくるだけ
git pull origin main          # 取ってきて、取り込む
```

`fetch` のあと、グラフには新しいコミットが現れ、`origin/main` はそこへ移ります。
**でも `main` は動きません。** これが fetch です。取ってくるだけで、合流はしません。

`pull` は、その fetch のあとに `git merge origin/main` を続けて実行します。それだけです。
今度は `main` も動きます。

### origin/main は「最後に見たとき」の記録

`origin/main` は**リモート追跡ブランチ**と呼ばれ、
「最後に fetch / push したとき、向こうの `main` がどこを指していたか」を覚えています。

自分では動きません。あなたが `fetch` するまで古いままです。
その古さが、そのまま「pull を忘れている」状態です。

### push が断られるとき

```
origin の main には、あなたが持っていないコミットがあります。
先に git pull origin main で取り込んでから、送り直してください。
```

push でいちばん出会うエラーですが、意味はこれだけです。
**向こうに、こちらの知らないコミットがある。** 直し方も 1 つで、先に取り込んでから送ります。

## 本物との違い

- ファイルの中身は持ちません。「変更があるかどうか」だけを持ちます
- コミット ID は本物の SHA-1 ではなく、7 桁の見た目だけ似せた文字列です
- ここでの操作は、あなたの実際のリポジトリには一切影響しません
- マージでコンフリクトは起きません。中身を持たないので、ぶつかりようがないためです（この章はあとで足します）
- rebase は作業中の変更があっても実行できます。本物の git は、そのままだと断ります
- rebase はマージコミットを置き直しません（本物の git も既定では落とします）
- リモートは同じブラウザの中の別の入れ物で、実際の通信はしていません

正確な仕様を知りたくなったら、[git-scm 公式ドキュメント](https://git-scm.com/doc)へどうぞ。
